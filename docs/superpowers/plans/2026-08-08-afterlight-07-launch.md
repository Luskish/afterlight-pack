# AFTERLIGHT Plan 07: VPS, Distribution, and Release Candidate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a reproducible VPS deployment, fail-closed maintenance tooling, friend installation assets, and a fully evidenced `0.9.0-rc.1` release candidate. Version `1.0.0` remains blocked until Shane completes the manual acceptance matrix.

**Architecture:** Docker Compose runs exact OCI-index digests for `itzg/minecraft-server` and `itzg/mc-backup` against one bind-mounted `/data` tree. A host ingress gate persists authenticated state outside `/data`, but every boot begins closed and every permissive rule is a short kernel lease backed by durable current-boot authorization plus an active fail-closed reconciler. One dedicated gate-transition lock serializes renewal, validation, close, status, reconciliation, and rule publication so an old authorization cannot restore a lease after close begins. Protected backup, install, update, rollback, and recovery fail closed through that gate. Every Task 3 data or active-release mutation writes authenticated intent before mutation, blocks unattended Compose, journals each boundary, and ends in exact resume, terminal success, authenticated safe abandonment, or an authenticated rollback-required failure. Rollback retains its stricter prepare, activate, consume, and finalize-only state machine. Every production opening requires fresh current-release, post-start health, and released-client join receipts for the exact active lineage. Pre-acceptance checks validate immutable inputs without requiring accepted `main`, current Pages, or a release Prism build; after skeptical review and all fixes, the final implementation commit becomes release subject SHA `S`, exact `S` is promoted to `main`, its completed successful `main` push workflow and Pages parity are accepted, and two fresh full release gauntlets run at `S`. The direct child evidence SHA `E` may change only the named release evidence documents, is promoted unchanged through `dev` and `main`, then receives separate external accepted-mode and exact client-release receipts before the annotated tag and GitHub release are created.

**Tech Stack:** Docker Compose, digest-pinned itzg images, Java 21, NeoForge 21.1.248, Packwiz installer bootstrap 0.0.3, Packwiz installer 0.5.14, Python 3.12 standard library, Bash, GitHub Actions, GitHub Pages, Chunky, and RCON.

## Global Constraints

- Minecraft is `1.21.1`; NeoForge is `21.1.248`; the container Java major is exactly 21.
- Default server memory is `INIT_MEMORY=4G`, `MAX_MEMORY=10G`, and `mem_limit: 13G`.
- Launch support is `linux/amd64`. OCI support for `linux/arm64` is recorded, but pack support remains unclaimed until its complete live matrix passes.
- No server address, credentials, RCON password, tokens, secrets, or generated RCON client files enter git or backup archives.
- `main` is the stable channel and `dev` is the working branch. Production staging uses raw full-SHA URLs, never mutable branch URLs.
- Pages is a parity gate only. The production container never sets `PACKWIZ_URL` and never downloads pack files at startup.
- Current mrpack and CurseForge exports contain embedded third-party JARs and remain friends-only.
- AutoModpack is disabled. It is neither a launch dependency nor a manual acceptance item while any exact artifact lacks affirmative redistribution permission.
- `${DATA_DIR}`, `${BACKUP_DIR}`, `${STATE_DIR}`, `${QUARANTINE_DIR}`, and `${SECRETS_DIR}` must be canonical, non-symlinked, pairwise nonnested paths. Data and quarantine must share a local filesystem for atomic rename. Maintenance, operation, and rollback authority must never live beneath `${DATA_DIR}` or inside a backup bundle.
- Every Bash operator script uses `#!/usr/bin/env bash`, `set -Eeuo pipefail`, `umask 077`, `LC_ALL=C`, and the same Linux operations lock at `${STATE_DIR}/ops.lock`.
- A top-level mutating command acquires the operations lock once, keeps one file descriptor open for its full lifetime, and exports that inherited descriptor to nested maintenance commands. An internal `--lock-held` path validates and reuses that descriptor instead of reacquiring the lock.
- Every gate state or kernel rule reader and writer uses root-owned `${STATE_DIR}/maintenance/gate.lock`. The fixed lock order is operations lock first, gate lock second. The reconciler takes only the gate lock for renewal and never waits for the operations lock while holding it. Remote release checks and other long work occur before the gate lock, followed by complete local revalidation while the gate lock is held.
- The host ingress gate is the only authority that can expose Minecraft TCP `25565` or voice UDP `24454`. Its permanent rules default to closed; every tester-only or production permission is one authenticated lease generation implemented only by `nftables` set elements with maximum 15-second kernel timeouts, renewed at most every 5 seconds only by the active reconciler. Missing, malformed, unauthenticated, stale, expired, unresolved, or live-rule-divergent state means closed.
- No gate transition may begin while an earlier maintenance intent lacks an authenticated terminal. `maintenance.sh reconcile` always resolves such an intent to a new proved-closed generation and never completes or recreates an interrupted open. Close owns a new transition generation before lease removal and proves zero permissive elements again before releasing the gate lock.
- Every host boot, including reboot from persisted `production-open`, installs and proves closed before Compose starts. Persisted open state is historical evidence only. Reopening requires current-boot accepted-release revalidation, a health receipt from the current container start, tester-only access, a released-client join attestation from that same boot and container, and a separate production-open command.
- No install, update, backup, rollback, recovery, health, Chunky, boot, or Compose command may infer or perform `production-open`. Only `maintenance.sh open --mode production` may do so, and it always requires fresh release, health, and join receipts. Rollback additionally requires the exact activated transaction.
- Common exit codes are `0` success, `2` usage or configuration, `3` live precondition, `4` trust or integrity, `5` operational failure, and `6` update stopped with an explicit rollback required.
- World mutation, update, rollback, recovery, and Chunky start or continue require a protected backup first. Every protected backup closes and proves the host ingress gate before archive creation, records the exact close intent, `committed` terminal, receipt, status proof, and detached digests, leaves the gate closed, and is never pruned automatically.
- Update health failure stops the server, leaves maintenance closed, preserves all evidence, writes one immutable rollback-request receipt containing the exact failed-state backup and bundle identity, and prints the exact operator runbook path. It never restores world data automatically or invents rollback SHA `R` before the operator creates and accepts it.
- Install, update, and recovery each create a durable operation intent and pending pointer before candidate, backup, RCON secret, service, `/data`, ledger, provenance, active-release, or health mutation. The one-time empty-host receipt-key bootstrap is the sole prerequisite exception and cannot touch `/data` or services. Any partial operation directory, unresolved pointer, or unsafe terminal failure blocks unattended Compose. Only the exact operation owner holding the operations lock may start Minecraft behind closed ingress for an authenticated resume or health phase.
- Rollback activation may expose only the authenticated tester allowlist. Production opening is a later explicit command that requires the fresh released-client join and health receipts for the same current boot, container, release, lineage, and consumed rollback transaction plus a freshly revalidated accepted receipt for the same rollback SHA.
- Pre-acceptance CI on `dev` or `main` must not require an already accepted `main` SHA, current Pages parity, `release_gate.py accept`, or a release Prism archive. The workflow run whose success establishes acceptance must never invoke accepted mode, gate itself, or wait for itself.
- Freeze release subject SHA `S` only after the whole-project skeptical review and every resulting fix. Promote exact `S` to `main`, accept its completed successful exact-SHA `main` push workflow and Pages parity, then run two clean full release gauntlets from separate fresh worktrees at `S`, each including `release_gate.py accept` and the release Prism build.
- Two accepted full gauntlets at `S` plus an explicit record of every deferred manual item permit `v0.9.0-rc.1`. Shane's manual matrix gates only `1.0.0` and claims that production is open.
- Evidence SHA `E` must be the direct child of `S` and may change only `docs/releases/v0.9.0-rc.1.md` and `docs/releases/v0.9.0-rc.1-gauntlet.md`. No executable, manifest, config, quest, pack, or workflow change is permitted from `S` to `E`.
- After exact `E` CI and Pages parity complete, an external operator process must run `release_gate.py accept` for `E`, then create an exact `afterlight.client.release.v1` receipt for `E` by read-only authentication of both byte-identical gauntleted `S` Prism archives and receipts. It must durably preserve both canonical receipts and detached SHA-256 files outside the repository before the annotated tag and GitHub release. Neither `E` nor the workflow being accepted may contain or generate those post-`E` receipts, and no `E` step may rebuild or rewrite the Prism archive.

## Durable State Layout

- `${STATE_DIR}/maintenance/gate.lock` is the dedicated gate-transition lock. `${STATE_DIR}/maintenance/boot.json` records the current Linux boot ID, a random boot nonce, the gate service start, and the mandatory boot-closed transition. `${STATE_DIR}/maintenance/state.json` records only the last completed transition for the current boot, including logical transition generation and exact live kernel generation. A persisted state from another boot can be audited but can never authorize a live rule.
- `${STATE_DIR}/maintenance/intents/<transition-id>.json` and `${STATE_DIR}/maintenance/open-authorizations/<transition-id>.json` are create-new authenticated transition records. `${STATE_DIR}/maintenance/terminals/<transition-id>.json` records exactly one terminal outcome, `committed` or `abandoned-closed`. An open authorization binds current boot and container IDs, current reconciler process epoch, exact active release and lineage, fresh accepted-release proof, health receipt, tester allowlist, join receipt when production is requested, expected predecessor and kernel generations, and a one-time nonce. It is flushed before any permissive lease and cannot be replayed on another boot, reconciler process, generation, or transition.
- `${STATE_DIR}/maintenance/receipts/<generation>.json` stores immutable completed transition receipts, `${STATE_DIR}/maintenance/proofs/<proof-id>.json` stores immutable status proofs, `${STATE_DIR}/maintenance/joins/<join-id>.json` stores general released-client attestations, and `${STATE_DIR}/health/<health-id>.json` stores health receipts. Health and join receipts expire after 600 seconds for use in a new transition and bind the current boot ID, container ID and start time, active release SHA and lineage, managed-ledger and provenance digests, logical and kernel gate generations, and predecessor receipt digests.
- `/run/afterlight-gate/reconciler.json` is root-owned runtime heartbeat state, not durable authority. Every reconciler startup acquires the operations lock then gate lock, reconciles any prior unterminated maintenance intent to `abandoned-closed`, create-new publishes a startup-close intent, removes all lease elements, creates a new random process epoch and kernel generation, publishes an authenticated current-boot closed transition plus `committed` terminal, and proves zero permissive elements before its loop. It then releases the operations lock. Each renewal takes only the gate lock across state and intent validation, lease replacement, kernel-generation proof, and heartbeat publication. A process death or restart invalidates every earlier authorization; a 10-second systemd watchdog turns a stall into a restart; and rule drift triggers closed rules plus Compose stop within one reconciliation interval.
- `${SECRETS_DIR}/maintenance-testers.txt` is the canonical mode `0600` tester CIDR allowlist. Gate receipts record only its SHA-256 and entry count, never its addresses. Every local record uses canonical UTF-8 JSON and HMAC-SHA-256 with `${SECRETS_DIR}/receipt-auth.key`; the key is mode `0600`, never logged, and never copied into `/data`, git, or backups.
- `${STATE_DIR}/host-bootstrap.json` authenticates the one-time empty-host trust initialization. `${STATE_DIR}/operations/pending.json` identifies at most one install, update, or recovery operation by ID, kind, phase, intent digest, and progress-chain tip. `${STATE_DIR}/operations/transactions/<operation-id>/` contains `intent.json`, `intent.json.sha256`, append-only `progress/<sequence>.json`, pre-operation and current inventories, `success.json`, `abandoned.json`, and `failed.json`. `${STATE_DIR}/operations/blockers/<operation-id>.json` is an authenticated persistent Compose blocker for a post-publication failure that cannot be safely abandoned, and `${STATE_DIR}/operations/resolved/<operation-id>.json` is its immutable resolution tombstone. Any transaction directory or temporary publication artifact without one exact valid resolution is itself fail-closed evidence, never ignored.
- `${STATE_DIR}/rollback/pending.json` identifies at most one prepared or activating transaction by ID, phase, and exact receipt digests. `${STATE_DIR}/rollback/transactions/<transaction-id>/` contains `prepare-intent.json`, `prepare-intent.json.sha256`, append-only `prepare-progress/<sequence>.json` records, `prepare.json`, `prepare.json.sha256`, `data-before.inventory`, `data-prepared.inventory`, `quarantine.inventory`, `prepare-abandoned.json`, `activation-intent.json`, `activation.json`, `activation-finalized.json`, `join.json`, and `production-open.json`. `${STATE_DIR}/rollback/consumed/<transaction-id>.json` is the durable one-time tombstone that prevents a completed prepare receipt from being reused.
- State directories are root-owned mode `0700`; lock files and mutable state are root-owned mode `0600`; immutable receipt, terminal, proof, digest, and inventory files become root-owned mode `0400` after durable publication. Gate, operation, and rollback records are written with create-new semantics, file `fsync`, atomic rename where replacement is required, and parent-directory `fsync`. They reject links, noncanonical paths, wrong ownership or mode, duplicate IDs, state beneath `/data`, and any receipt whose schema, HMAC, predecessor digest, boot ID, generation, or digest chain does not validate.
- Final release acceptance uses separate canonical, remotely authenticated receipts. The external release operator stores `E-acceptance.json`, `E-acceptance.json.sha256`, `E-client-release.json`, and `E-client-release.json.sha256` beneath canonical `${RELEASE_STATE_DIR}/v0.9.0-rc.1/` outside every Git worktree. These files are public-safe evidence, not VPS HMAC records, and are copied into annotated-tag and GitHub-release metadata rather than committed.
