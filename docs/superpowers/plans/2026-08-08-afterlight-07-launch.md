# AFTERLIGHT Plan 07: VPS, Distribution, and Release Candidate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a reproducible VPS deployment, fail-closed maintenance tooling, friend installation assets, and a fully evidenced `0.9.0-rc.1` release candidate. Version `1.0.0` remains blocked until Shane completes the manual acceptance matrix.

**Architecture:** Docker Compose runs exact OCI-index digests for `itzg/minecraft-server` and `itzg/mc-backup` against one bind-mounted `/data` tree. A host ingress gate persists authenticated state outside `/data`, but every boot begins closed and every permissive rule is a short kernel lease backed by durable current-boot authorization plus an active fail-closed reconciler. One dedicated gate-transition lock serializes renewal, validation, close, status, reconciliation, and rule publication so an old authorization cannot restore a lease after close begins. Every renewal also refreshes a 15-second authenticated current-`main` and Pages freshness lease, and drift or refresh failure closes immediately. Protected backup, install, update, rollback, and recovery fail closed through that gate. Every Task 3 data or active-release mutation atomically publishes one self-contained authenticated pending bootstrap as its first durable authority, blocks unattended Compose, journals each boundary, and ends in exact resume, terminal success, authenticated safe abandonment, or an authenticated rollback-required failure. Only the exact active transaction may cross a reboot or container replacement through chained boot-continuation and health-supersession records, with every earlier health receipt retained. Rollback retains its stricter prepare, activate, consume, and finalize-only state machine, and its RCON-free backup path is internal to the authenticated prepare transaction. Maintenance reconciliation is itself one crash-resumable transaction shared by startup and manual invocation. Every production opening requires fresh current-release, post-start health, and released-client join receipts for the exact active lineage. Pre-acceptance checks validate immutable inputs without requiring accepted `main`, current Pages, or a release Prism build; after skeptical review and all fixes, the final implementation commit becomes release subject SHA `S`, exact `S` is promoted to `main`, its completed successful `main` push workflow and Pages parity are accepted, and two fresh full release gauntlets run at `S`. The direct child evidence SHA `E` may change only the named release evidence documents, is promoted unchanged through `dev` and `main`, then receives separate external accepted-mode and exact client-release receipts before the annotated tag and GitHub release are created.

**Tech Stack:** Docker Compose, digest-pinned itzg images, Java 21, NeoForge 21.1.248, Packwiz installer bootstrap 0.0.3, Packwiz installer 0.5.14, Python 3.12 standard library, Bash, GitHub Actions, GitHub Pages, Chunky, and RCON.

## Global Constraints

- Minecraft is `1.21.1`; NeoForge is `21.1.248`; the container Java major is exactly 21.
- Default server memory is `INIT_MEMORY=4G`, `MAX_MEMORY=10G`, and `mem_limit: 13G`.
- Launch support is `linux/amd64`. OCI support for `linux/arm64` is recorded, but pack support remains unclaimed until its complete live matrix passes.
- No server address, credentials, RCON password, tokens, secrets, or generated RCON client files enter git or backup archives.
- `main` is the stable channel and `dev` is the working branch. Production staging uses raw full-SHA URLs, never mutable branch URLs.
- Pages is a parity gate only. The production container never sets `PACKWIZ_URL` and never downloads pack files at startup.
- Current mrpack and CurseForge exports contain embedded third-party JARs and remain friends-only.
- AutoModpack is disabled. It is neither a launch dependency nor a manual acceptance item while any exact artifact lacks affirmative redistribution permission.
- `${DATA_DIR}`, `${BACKUP_DIR}`, `${STATE_DIR}`, `${QUARANTINE_DIR}`, and `${SECRETS_DIR}` must be canonical, non-symlinked, pairwise nonnested paths. Data and quarantine must share a local filesystem for atomic rename. Maintenance, operation, and rollback authority must never live beneath `${DATA_DIR}` or inside a backup bundle.
- Every Bash operator script uses `#!/usr/bin/env bash`, `set -Eeuo pipefail`, `umask 077`, `LC_ALL=C`, and the same Linux operations lock at `${STATE_DIR}/ops.lock`.
- A top-level mutating command acquires the operations lock once, keeps one file descriptor open for its full lifetime, and exports that inherited descriptor to nested maintenance commands. An internal `--lock-held` path validates and reuses that descriptor instead of reacquiring the lock.
- Every gate state or kernel rule reader and writer uses root-owned `${STATE_DIR}/maintenance/gate.lock`. The fixed lock order is operations lock first, gate lock second. A renewal takes one short gate-locked snapshot, performs its bounded remote current-channel probe with no lock held, then retakes the gate lock and completely revalidates the snapshot before freshness publication or rule replacement. The reconciler never waits for the operations lock while holding the gate lock.
- The host ingress gate is the only authority that can expose Minecraft TCP `25565` or voice UDP `24454`. Its permanent rules default to closed; every tester-only or production permission is one authenticated lease generation implemented only by `nftables` set elements with maximum 15-second kernel timeouts, renewed at most every 5 seconds only by the active reconciler. Every renewal must create a new authenticated freshness generation proving current remote `main`, exact raw release bytes, current Pages deployment, and byte parity for the active SHA. Freshness uses current-boot `CLOCK_BOOTTIME` nanoseconds, not adjustable wall time, and expires exactly 15,000,000,000 nanoseconds after issuance. The kernel timeout is rounded down to the remaining freshness lifetime and may never outlive it. Missing, malformed, unauthenticated, stale, expired, unresolved, remote-refresh-failed, channel-drifted, or live-rule-divergent state means immediate closed rules plus Compose stop.
- No gate transition may begin while an earlier maintenance intent or reconciliation lacks an authenticated terminal. Manual and startup reconciliation use one idempotent protocol with an atomic pending bootstrap, append-only progress generations, exact replay, the interrupted transition's `abandoned-closed` terminal, a reconciliation terminal, and pending cleanup. Startup may remove lease elements first as an emergency safety action, but it must record detection and run or resume that same protocol before Compose or another transition. Reconciliation never completes or recreates an interrupted open. Close owns a new transition generation before lease removal and proves zero permissive elements again before releasing the gate lock.
- Every host boot, including reboot from persisted `production-open`, installs and proves closed before Compose starts. Persisted open state is historical evidence only. Reopening requires current-boot accepted-release revalidation, a health receipt from the current container start, tester-only access, a released-client join attestation from that same boot and container, and a separate production-open command.
- No install, update, backup, rollback, recovery, health, Chunky, boot, or Compose command may infer or perform `production-open`. Only `maintenance.sh open --mode production` may do so, and it always requires fresh release, health, and join receipts. Rollback additionally requires the exact activated transaction.
- Common exit codes are `0` success, `2` usage or configuration, `3` live precondition, `4` trust or integrity, `5` operational failure, and `6` update stopped with an explicit rollback required.
- World mutation, update, rollback, recovery, and Chunky start or continue require a protected backup first. Every protected backup closes and proves the host ingress gate before archive creation, records the exact close intent, `committed` terminal, receipt, status proof, and detached digests, leaves the gate closed, and is never pruned automatically. The offline `.paused` branch is not a public backup mode. It is available only to an authenticated rollback prepare parent whose pending bootstrap, inherited operations lock, stopped-service proof, marker intent, and marker identity all validate.
- Update health failure stops the server, leaves maintenance closed, preserves all evidence, writes one immutable rollback-request receipt containing the exact failed-state backup and bundle identity, and prints the exact operator runbook path. It never restores world data automatically or invents rollback SHA `R` before the operator creates and accepts it.
- Install, update, and recovery each atomically publish one authenticated `${STATE_DIR}/operations/pending.json` envelope containing the complete immutable bootstrap intent and active pointer before candidate, backup, RCON secret, service, `/data`, ledger, provenance, active-release, or health mutation. There is no separately durable intent, digest, or pointer window. The one-time empty-host receipt-key bootstrap is the sole prerequisite exception and cannot touch `/data` or services. Any unresolved envelope, unexplained transaction record, or unsafe terminal failure blocks unattended Compose. Only its exact owner holding the operations lock may start Minecraft behind closed ingress, publish a same-transaction boot continuation, or supersede stale health.
- Before a normal post-launch update promotes a candidate to `main`, `update.sh authorize-promotion` must atomically create an authenticated promotion guard, close and prove maintenance, and publish a closure receipt binding candidate SHA, predecessor `main`, active release, boot, gate generations, zero leases, and zero players. The guard blocks every open transition until the operator either records that exact promotion and transfers it into the update bootstrap or safely abandons it while remote `main` is still the predecessor. No maintenance script performs the Git push.
- Rollback activation may expose only the authenticated tester allowlist. Production opening is a later explicit command that requires the fresh released-client join and health receipts for the same current boot, container, release, lineage, and consumed rollback transaction plus a freshly revalidated accepted receipt for the same rollback SHA. Before consumption, only the exact activating transaction may continue across a new boot or container and supersede its stale closed-health receipt. After consumption, ordinary resume remains forbidden.

## Durable State Layout

- `${STATE_DIR}/maintenance/gate.lock` is the dedicated gate-transition lock. `${STATE_DIR}/maintenance/boot.json` records the current Linux boot ID, a random boot nonce, the gate service start, and the mandatory boot-closed transition. `${STATE_DIR}/maintenance/state.json` records only the last completed transition for the current boot, including logical transition generation and exact live kernel generation. A persisted state from another boot can be audited but can never authorize a live rule.
- `${STATE_DIR}/maintenance/intents/<transition-id>.json` and `${STATE_DIR}/maintenance/open-authorizations/<transition-id>.json` are create-new authenticated transition records. `${STATE_DIR}/maintenance/terminals/<transition-id>.json` records exactly one terminal outcome, `committed` or `abandoned-closed`. An open authorization binds current boot and container IDs, current reconciler process epoch, exact active release and lineage, fresh accepted-release proof, health receipt, tester allowlist, join receipt when production is requested, expected predecessor and kernel generations, and a one-time nonce. It is flushed before any permissive lease and cannot be replayed on another boot, reconciler process, generation, or transition.
- `${STATE_DIR}/maintenance/detections/<detection-id>.json` stores create-new `afterlight.maintenance.reconcile.detection.v1` records written after startup emergency closure. The detection ID is the SHA-256 of the canonical interrupted transition ID and intent digest, so a kill after detection but before pending publication can only reuse that exact record; a collision with different bytes is a blocker. Each detection binds entry point, current and prior boot, interrupted transition and intent, authorization and terminal observations, live-rule and lease digests, emergency-close result, and issue times. `${STATE_DIR}/maintenance/reconcile-pending.json` is one self-contained `afterlight.maintenance.reconcile.pending.v1` envelope naming that detection or authenticated null, the interrupted transition, its intent and authorization digests, observed boot and kernel state, reconciliation ID, pending generation, phase exactly `reconciling` or `terminalizing-cleanup`, progress generation and tip, transaction path, and HMAC. `${STATE_DIR}/maintenance/reconciliations/<reconciliation-id>/` retains `bootstrap.json`, byte-identical later pending generations at `pending-generations/<generation>.json`, append-only `afterlight.maintenance.reconcile.progress.v1` records at `progress/<generation>.json`, close receipts and proofs, and one `afterlight.maintenance.reconcile.terminal.v1` with outcome `committed-closed`. Progress binds sequence, predecessor digest, step name, before and after observations, owned generations, and expected next step. Startup and manual entry points may create or resume only this exact transaction. The interrupted transition terminal is published before the reconciliation terminal. The final progress record is a cleanup intent binding both terminals and expected pending bytes; pending then advances to `terminalizing-cleanup`, and unlink plus parent-directory `fsync` are the final writes. No post-unlink record exists. If killed after unlink, absence plus the matching terminal and cleanup intent proves completion; if pending survives, exact replay repeats only unlink and `fsync`. Detection records remain immutable evidence and are resolved only by their bound reconciliation terminal.
- `${STATE_DIR}/maintenance/channel-freshness/leases/<generation>.json` stores immutable `afterlight.maintenance.channel-freshness.v1` records. Each record binds repository, active SHA and lineage, accepted-receipt digest, remote `main` object ID, raw and Pages `pack.toml` and `index.toml` hashes, Pages deployment ID, boot, reconciler epoch, open authorization nonce, predecessor freshness digest, `issued_boottime_ns`, `expires_boottime_ns` exactly 15,000,000,000 greater, and an informational UTC issue time. Issuance occurs under the gate lock after the successful remote probe and complete local revalidation. `${STATE_DIR}/maintenance/channel-freshness/current.json` is an atomically replaced authenticated pointer. Open transition receipts, open-mode health, join, status, heartbeat, and kernel-rule proofs bind the applicable freshness digest. Another boot, an unavailable `CLOCK_BOOTTIME`, a nonpositive remaining lifetime, or any expiry mismatch fails closed.
- `${STATE_DIR}/maintenance/receipts/<generation>.json` stores immutable completed transition receipts, `${STATE_DIR}/maintenance/proofs/<proof-id>.json` stores immutable status proofs, `${STATE_DIR}/maintenance/joins/<join-id>.json` stores general released-client attestations, and `${STATE_DIR}/health/<health-id>.json` stores health receipts. Transaction health IDs are deterministic `<kind>-<transaction-id>-<health-sequence>` values, with sequence zero for initial health and a strictly increasing sequence for each new container. Health and join receipts expire after 600 seconds for use in a new transition and bind the current boot ID, container ID and start time, active release SHA and lineage, managed-ledger and provenance digests, logical and kernel gate generations, applicable freshness digest or authenticated null, active transaction, boot-continuation tip, superseded-health digest, and predecessor health-supersession tip or authenticated nulls, and predecessor receipt digests. The later supersession record binds the new health, then becomes the active pending or consumed chain tip.
- `/run/afterlight-gate/reconciler.json` is root-owned runtime heartbeat state, not durable authority. Every reconciler startup acquires the operations lock then gate lock, forces live rules closed, records any unresolved transition detection, runs or resumes the one reconciliation protocol, create-new publishes a startup-close intent, creates a new random process epoch and kernel generation, publishes an authenticated current-boot closed transition plus `committed` terminal, and proves zero permissive elements before its loop. It then releases the operations lock. Each open-mode loop takes a gate-locked snapshot, performs one remote freshness probe with a four-second overall deadline and no lock held, then retakes the gate lock for complete revalidation, freshness publication, lease replacement, kernel-generation proof, and heartbeat publication. A process death or restart invalidates every earlier authorization; a 10-second systemd watchdog turns a stall into a restart; and refresh failure, channel drift, or rule drift triggers immediate closed rules plus Compose stop.
- `${SECRETS_DIR}/maintenance-testers.txt` is the canonical mode `0600` tester CIDR allowlist. Gate receipts record only its SHA-256 and entry count, never its addresses. Every local record uses canonical UTF-8 JSON and HMAC-SHA-256 with `${SECRETS_DIR}/receipt-auth.key`; the key is mode `0600`, never logged, and never copied into `/data`, git, or backups.
- `${STATE_DIR}/host-bootstrap.json` authenticates the one-time empty-host trust initialization. `${STATE_DIR}/operations/pending.json` is the complete `afterlight.operation.pending.v1` bootstrap envelope for at most one install, update, or recovery operation. It contains the full immutable intent payload, operation ID and kind, pending generation, phase `bootstrapped`, `mutating`, `health`, `terminalizing-success`, `terminalizing-failure`, or `terminalizing-abandonment`, bound transaction path, publication nonce, predecessor pending and terminal digests, progress tip, boot-continuation tip, health-supersession tip, promotion-closure and promotion-observation digests or authenticated nulls, and HMAC. `${STATE_DIR}/operations/transactions/<operation-id>/` retains the exact first envelope as `bootstrap.json`, byte-identical later pending generations at `pending-generations/<generation>.json`, append-only `progress/<sequence>.json`, `boot-continuations/<sequence>.json`, `health-supersessions/<sequence>.json`, pre-operation and current inventories, and exactly one applicable `success.json`, `abandoned.json`, or `failed.json`. `${STATE_DIR}/operations/blockers/<operation-id>.json` is an authenticated persistent Compose blocker for a post-publication failure that cannot be safely abandoned, and `${STATE_DIR}/operations/resolved/<operation-id>.json` is its immutable resolution tombstone.
- `${STATE_DIR}/operations/promotions/pending.json` is an atomic `afterlight.update.promotion.pending.v1` guard with pending generation; phase `closing`, `closed-authorized`, `observed`, or `transferring`; promotion ID; candidate and predecessor SHAs; active-release and current-acceptance digests; boot and gate generations; transaction path; prior pending digest; close and observation digests when applicable; and HMAC. `${STATE_DIR}/operations/promotions/transactions/<promotion-id>/` retains `bootstrap.json`, byte-identical later pending generations at `pending-generations/<generation>.json`, close intent and terminal, closed status proof, `closure.json`, optional `observed.json`, and exactly one `consumed.json` or `abandoned.json`. A pending guard blocks tester and production opening. The exact update bootstrap must bind and consume it before removal; safe abandonment is legal only while remote `main` still equals the bound predecessor.
- `${STATE_DIR}/rollback/pending.json` is the complete `afterlight.rollback.pending.v1` bootstrap and active pointer with pending generation and phase exactly `preparing`, `prepared`, or `activating`. It embeds the full prepare intent, transaction ID, transaction path, progress tip, predecessor pending digest, prepare-receipt digest or authenticated null, activation-intent digest or authenticated null, boot-continuation tip or authenticated null, health-supersession tip or authenticated null, and HMAC. `${STATE_DIR}/rollback/transactions/<transaction-id>/` retains `bootstrap.json`, byte-identical later pending generations at `pending-generations/<generation>.json`, append-only `prepare-progress/<sequence>.json`, `boot-continuations/<sequence>.json`, `health-supersessions/<sequence>.json`, `prepare.json`, `prepare.json.sha256`, full inventories, `prepare-abandoned.json`, the archived activation intent, `activation.json`, `activation-finalized.json`, `join.json`, and `production-open.json`. `${STATE_DIR}/rollback/consumed/<transaction-id>.json` is the durable one-time tombstone that prevents a completed prepare receipt from being reused. Marker intent, exact authenticated `.paused` contents, inode and digest, creation and removal directory flushes, and backup observations live in the prepare progress chain.
- The first authoritative publication of each operation, rollback prepare, update-promotion guard, or maintenance reconciliation is pending generation zero and one complete envelope. On Linux it is written to an unnamed same-directory `O_TMPFILE`, file-flushed, linked create-new to the final pending path with `linkat(AT_EMPTY_PATH)`, then parent-directory-flushed before any protected mutation. A kill before the link leaves no named state; a kill before the directory flush yields either no envelope and no mutation or the complete envelope. Unsupported `O_TMPFILE` or `linkat` behavior fails host preflight. After that flush, the owner creates and flushes the transaction directory and byte-identical create-new `bootstrap.json`. If killed first, only the matching pending envelope may reconstruct those exact embedded bytes. Every later pending generation increments by one, binds the prior pending digest, and is first create-new and flushed at its transaction `pending-generations/<generation>.json`; identical bytes then replace the top-level pointer through a same-directory file-flushed temporary, atomic rename, and parent-directory flush. A kill with exactly one valid archived generation ahead of the pointer may adopt only that generation after complete state revalidation. A pointer without its matching later-generation archive, a skipped generation, or multiple next generations blocks. Immutable records use create-new, file `fsync`, and parent-directory `fsync`.
- A boot continuation is create-new and parent-flushed before the exact active owner starts or replaces a transaction-owned service or container on a new boot. Old container and health fields are exact values or authenticated nulls. The pending envelope then atomically advances to a new generation binding the continuation digest and predecessor pending digest, and its parent is flushed before start. A fresh health receipt is create-new and parent-flushed. When an older transaction health exists, a create-new health-supersession record binds both health digests, both boot and container identities, the continuation and progress tips, active release and lineage, gate generations, and predecessor supersession tip; the pending envelope then atomically advances to bind this new tip. Both parent flushes precede terminal success, a not-yet-published activation, or rollback consumption. Exactly one valid next continuation or supersession record beyond the pending tip may be adopted by exact resume; any second, skipped, or mismatched record is a blocker. An already durable pre-consumption activation remains immutable and is extended only because the consumed tombstone binds its digest plus the newer chain tips. Prior health is never overwritten or deleted. A same-boot container replacement requires health supersession even when no boot continuation is needed.
- State directories are root-owned mode `0700`; lock files and mutable state are root-owned mode `0600`; immutable receipt, terminal, proof, digest, inventory, continuation, and supersession files become root-owned mode `0400` after durable publication. Records reject links, noncanonical paths, wrong ownership or mode, duplicate IDs, state beneath `/data`, and any schema, HMAC, predecessor, boot, generation, or chain mismatch. An unexplained record remains a blocker. The only reconstructable lag is a missing immutable transaction copy whose exact bytes are still embedded in the matching authenticated pending envelope.
- Final release acceptance uses separate canonical, remotely authenticated receipts. The external release operator stores `E-acceptance.json`, `E-acceptance.json.sha256`, `E-client-release.json`, and `E-client-release.json.sha256` beneath canonical `${RELEASE_STATE_DIR}/v0.9.0-rc.1/` outside every Git worktree. These files are public-safe evidence, not VPS HMAC records, and are copied into annotated-tag and GitHub-release metadata rather than committed.

**Interfaces:**
- `release_gate.py preaccept --repo OWNER/REPO --sha SHA` validates the immutable subject and repository inputs without requiring current `main`, Pages, a completed acceptance workflow, or Prism. It prints a mode-labeled JSON result and never prints an acceptance receipt.
- `release_gate.py accept --repo OWNER/REPO --sha SHA --pages-url URL --receipt-out RECEIPT --digest-out DIGEST` requires current `main`, the already completed successful exact-SHA `main` push workflow and job, the exact Pages deployment, Pages byte parity, and clean client and server installs. It creates one canonical authenticated JSON receipt plus its detached SHA-256 with create-new, flush, and parent-directory durability, then exits `0`; any failure exits `4` without either final file.
- `release_gate.py historical --repo OWNER/REPO --sha SHA` authenticates an earlier completed successful `main` push workflow and immutable raw release bytes for backup validation, rollback preparation, or recovery. It never treats historical evidence as permission to reopen against a different current client channel.
- `release_gate.py current-channel --repo OWNER/REPO --sha SHA --pages-url URL --acceptance-receipt RECEIPT --deadline-seconds 4` is a read-only bounded probe for the gate reconciler. It requires remote `main` to remain exact `SHA`, authenticates the supplied acceptance receipt, resolves the current Pages deployment, and compares cache-busted Pages `pack.toml` and `index.toml` bytes with immutable raw full-SHA bytes. It emits canonical probe facts to stdout only after success and never writes a receipt, installs a pack, or reuses a prior response after timeout or error.
- `lib.sh` exposes fixed Compose invocation, canonical path checks, dependency checks, one inherited Linux operations-lock file descriptor, the dedicated gate-transition lock with enforced lock ordering, HTTPS download with SHA-256 verification, RCON execution, and guarded temporary-directory cleanup.
- `maintenance.sh close --reason TOKEN [--lock-held]` owns a new logical and kernel generation, removes every permissive lease, invalidates and directory-flushes the current freshness pointer, and re-proves zero lease elements before publishing closed. `maintenance.sh status [--require closed|tester-only|production-open] [--receipt-out RECEIPT] [--lock-held]` takes the gate lock and proves current-boot durable state, freshness when open, kernel lease, reconciler heartbeat, live rules, connections, service, and player observations.
- `maintenance.sh open --mode tester-only --release-receipt RECEIPT --health-receipt RECEIPT [--transaction TRANSACTION] [--lock-held]` freshly reruns accepted-mode remote and Pages validation, compares the canonical result to the supplied release receipt, validates current-boot health and lineage, then creates one tester lease authorization. `maintenance.sh open --mode production` requires the same arguments plus `--join-receipt RECEIPT`; no production invocation makes transaction or join evidence optional.
- `maintenance.sh reconcile --intent INTENT --confirm TRANSITION_ID [--lock-held]` starts, resumes, or idempotently verifies the one matching reconciliation transaction. It derives the deterministic detection path and must bind an existing matching startup detection instead of substituting authenticated null. An internal `--auto-detected DETECTION --lock-held` entry point is used only by the boot gate and reconciler services. Both entry points share the same atomic bootstrap, progress, close, original-terminal, reconciliation-terminal, and pointer-cleanup protocol. They invalidate the interrupted authorization, close into new logical and kernel generations, and never resume an interrupted open.
- `maintenance.sh attest-join --release-receipt RECEIPT --health-receipt RECEIPT --client-release-receipt RECEIPT --confirm SHA --receipt-out RECEIPT [--transaction TRANSACTION] [--lock-held]` is the general released-client join interface for install, update, reboot, protected-maintenance return, and rollback. It requires tester-only mode and creates one current-boot join receipt at a new canonical path beneath `${STATE_DIR}/maintenance/joins/`. `rollback.sh attest-join` delegates to this interface and adds the exact consumed transaction and activation digests at its fixed transaction receipt path.
- `gate_reconciler.py` runs only under `afterlight-gate-reconciler.service`, closes into a new process epoch before its first loop, and checks at least every 5 seconds. In an open mode it takes a gate-locked snapshot, releases the lock for one four-second `current-channel` probe, then retakes the gate lock and holds it from complete snapshot revalidation through freshness publication, atomic lease replacement, kernel-generation proof, and heartbeat publication. Probe failure or drift takes the gate lock and immediately begins a fail-closed transition for the still-matching generation. It has no interface that can create an open authorization or convert tester-only to production.
