# AFTERLIGHT Plan 07: VPS, Distribution, and Release Candidate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a reproducible VPS deployment, fail-closed maintenance tooling, friend installation assets, and a fully evidenced `0.9.0-rc.1` release candidate. Version `1.0.0` remains blocked until Shane completes the manual acceptance matrix.

**Architecture:** Docker Compose runs exact OCI-index digests for `itzg/minecraft-server` and `itzg/mc-backup` against one bind-mounted `/data` tree. A host ingress gate persists authenticated state outside `/data`, but every boot begins closed and every permissive rule is a short kernel lease backed by durable current-boot authorization plus an active fail-closed reconciler. One dedicated gate-transition lock serializes renewal, validation, close, status, reconciliation, and rule publication so an old authorization cannot restore a lease after close begins. Every renewal also refreshes a 15-second authenticated current-`main` and Pages freshness lease, and drift or refresh failure closes immediately. One authenticated epoch-compaction state machine bounds that freshness journal without deleting any generation referenced by live state or unexpired evidence. Protected backup, install, update, rollback, and recovery fail closed through that gate. One common publication engine gives every immutable local or external record atomic no-clobber visibility and gives every mutable pointer one deterministic, crash-adoptable replacement path. Every Task 3 data or active-release mutation atomically publishes one self-contained authenticated pending bootstrap as its first durable authority, blocks unattended Compose, journals each boundary, and ends in exact resume, terminal success, authenticated safe abandonment, or an authenticated rollback-required failure. Only the exact active transaction may cross a reboot or container replacement through chained boot-continuation and health-supersession records, with every earlier health receipt retained. A failed normal promotion terminalizes its candidate attempt while the host remains closed, and the same single authority may transfer only to an explicitly authorized fast-forward successor. Rollback retains its stricter prepare, activate, consume, and finalize-only state machine, and its RCON-free backup path is internal to the authenticated prepare transaction. Maintenance reconciliation is itself one crash-resumable transaction shared by startup and manual invocation. Every production opening requires fresh current-release, post-start health, and released-client join receipts for the exact active lineage. Pre-acceptance checks validate immutable inputs without requiring accepted `main`, current Pages, or a release Prism build; after skeptical review and all fixes, the final implementation commit becomes release subject SHA `S`, exact `S` is promoted to `main`, its completed successful `main` push workflow and Pages parity are accepted, and two fresh full release gauntlets run at `S`. The direct child evidence SHA `E` may change only the named release evidence documents, is promoted unchanged through `dev` and `main`, then receives separate external accepted-mode and exact client-release receipt and digest pairs through idempotent external retries before the annotated tag and GitHub release are created.

**Tech Stack:** Docker Compose, digest-pinned itzg images, Java 21, NeoForge 21.1.248, Packwiz installer bootstrap 0.0.3, Packwiz installer 0.5.14, Python 3.12 standard library, Bash, GitHub Actions, GitHub Pages, Chunky, and RCON.

A renewal takes one short gate-locked snapshot, performs its bounded remote current-channel probe with no lock held, then retakes the gate lock and completely revalidates the snapshot before freshness publication or rule replacement. The reconciler never waits for the operations lock while holding the gate lock.

Canonical bytes are complete before staging; the staged inode receives its exact owner and final mode and is file-flushed before a create-new final link; the parent is flushed before success. No writer opens a final immutable pathname for writing. Mutable pointers use the same staged-inode preparation plus one owner-derived replacement name, an authenticated predecessor, atomic rename, and parent flush. It never replaces valid immutable evidence, and any partial, conflicting, extra, wrongly owned, or noncanonical named state blocks.
- The host ingress gate is the only authority that can expose Minecraft TCP `25565` or voice UDP `24454`. Its permanent rules default to closed; every tester-only or production permission is one authenticated lease generation implemented only by `nftables` set elements with maximum 15-second kernel timeouts, renewed at most every 5 seconds only by the active reconciler. Every renewal must create a new authenticated freshness generation proving current remote `main`, exact raw release bytes, current Pages deployment, and byte parity for the active SHA. Freshness uses current-boot `CLOCK_BOOTTIME` nanoseconds, not adjustable wall time, and expires exactly 15,000,000,000 nanoseconds after issuance. The kernel timeout is rounded down to the remaining freshness lifetime and may never outlive it. Missing, malformed, unauthenticated, stale, expired, unresolved, remote-refresh-failed, channel-drifted, or live-rule-divergent state means immediate closed rules plus Compose stop.
- The shared freshness store is the sole writer, retention owner, and compactor for `${STATE_DIR}/maintenance/channel-freshness/`; it accepts only a caller that proves ownership of the canonical gate-lock file descriptor. Issuance is globally rate-limited to one generation per 5,000,000,000 `CLOCK_BOOTTIME` nanoseconds, including first-open generations. The 600-second evidence window therefore references at most 121 distinct finite-window generations, and exactly one current open lineage may add one older live-until-close anchor. Before either the 128-file or 1 MiB soft limit the store must checkpoint and compact. Each lease is at most 8192 bytes and each checkpoint is at most 262,144 bytes.
